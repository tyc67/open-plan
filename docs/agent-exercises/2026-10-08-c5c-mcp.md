Claude Code and Codex each used the Open Plan MCP server: first a check of all ten tools on test files, then a full run from the real floor-plan image to a plan, and then a change by the agent while the plan was open in `serve` (roadmap C5c). Gemini CLI, Cursor and OpenCode are not in this record; they are C5d. This record holds no image and no plan file; it gives their full SHA-256 values. The image, the plans, the logs, the packed CLI, the harness, the prompts and the screenshots are kept locally, outside the repository, in `~/Documents/open-plan-agent-exercises/2026-10-08-c5c/`.

## Configuration of each client

**Claude Code:**

```sh
claude -p "$prompt" --model claude-opus-5-5 --tools Read --strict-mcp-config --mcp-config harness/mcp-<folder>.json \
  --setting-sources project,local --allowedTools "Read mcp__open-plan" --output-format stream-json --verbose [--resume <session>]
```

with `mcp-<folder>.json` = `{"mcpServers":{"open-plan":{"command":"node","args":["<harness>/mcp-log.mjs","<folder>","--root","<absolute folder>"]}}}`. The session's init event lists exactly 11 tools: `Read` and the ten `mcp__open-plan__*` tools, and one MCP server, `open-plan`, connected. `Read` cannot write files, so in these runs **only the Open Plan tools could write files**: this is a proof by configuration, from the client's own tool list.

**Codex:**

```sh
codex exec -i <folder>/floorplan.jpg -C <folder> --skip-git-repo-check --ignore-user-config --ignore-rules --json -m gpt-6.1-sol \
  -c 'model_reasoning_effort="low"' -c 'sandbox_mode="workspace-write"' \
  -c features.shell_tool=false -c features.unified_exec=false -c features.apps=false \
  -c 'mcp_servers.open-plan.default_tools_approval_mode="approve"' \
  -c 'mcp_servers.open-plan.command="node"' -c 'mcp_servers.open-plan.args=["<harness>/mcp-log.mjs","<folder>","--root","<absolute folder>"]'
```

**Codex tools that stayed available.** `codex exec` gives no init event with a tool list. ## Geometry against the image

**Human check: not done.** No person compared the plans with the image. The findings below come from automated checks and from looking at the overlay pictures; they are not a pass of the drawing. Validity and client compatibility are not drawing accuracy.

**Wall types and openings:**

- **Claude Code:** 10 exterior, 5 bearing, 9 interior and 8 low walls; 8 windows, 1 sliding door, 7 doors. Sills and heads from the labels, for example "窗高234 離地5" → sill 50, head 2390. The labels give widths in cm (307 = 3070 mm), so the sills of 40 to 70 mm agree with the labels read as cm; a person did not check them. Three heights were not readable and are its estimates.
- **Codex:** 11 exterior, 13 interior, 8 bearing and 13 low walls (the balcony edges are now low walls); 16 doors, 1 sliding door, 5 windows, 2 holes. **Every window has the default sill 900 and head 2400**, although the guide says to use the heights that the drawing gives.

**Window widths against the labels** (each plan window matched to the nearest label width; a rough method, because a window is not matched by its position):

- **Claude Code:** 2360 and 2140 exactly; 3120 → 2950 (−5.4 %); 1620 → 1500 (Claude Code reported that it shortened it); 3070 → 2950.
- **Codex:** no width is close to most labels; with an assumed scale and no label reading, the widths are estimates.

**Wall overlay (pixel masks, the C4b method).** Each plan was drawn with `render --no-text` at the agent's own scale and fitted onto the image by position and a scale adjustment, with the C4b script and thresholds (`evidence/overlay/overlay-fit.mjs`). These are **pixel-mask proximities, not verified percentages of real walls**: the plan mask leaves out low walls and includes door arcs; the image mask includes some symbols.

## Harness incidents

- **Codex `-i` start failure:** the first full-run command put `-i <image>` after other options; `-i` takes several values, so it read the prompt as an image path, and Codex stopped with "No prompt provided via stdin." before any model call or tool call (`harness/logs/run-codex-0-failed-start.*`, kept). The runner now puts `-i` first; the run `run-codex-1` is the one recorded above.
- **Runner edited during a run:** `run.sh` was edited while the Claude Code full run was running. After the `claude` command ended, the shell read the changed file and stopped with "line 32: unexpected EOF". The Claude Code run itself had ended; its log, its result event and its plan file are complete, so the result is not affected. After this, the runner was not edited during a run.

## Result

- **C5c, Claude Code and Codex:** the MCP server connects, all ten tools give their expected results through both clients, and each agent made a plan from the real image through the MCP tools; the plans pass `validate_plan` and the CLI `validate`, import in the website, draw in 2D and 3D, and a later MCP change appears in the open `serve` editor within 60 ms of the file change.
- **MCP-only condition:** met by configuration for Claude Code (only `Read` and the Open Plan tools). For Codex, not verified: every retained plan version matches an MCP write, but `apply_patch`, a code runtime and sub-agents stayed available and code-runtime calls are not in its log. The user accepted this deviation (2026-10-08).
- **Known errors:** the geometry errors above (missing interior walls in Claude Code's plan; extra walls and doors, default window heights and an assumed scale in Codex's plan). Not checked by a person.
- **Workspace boundary (remaining limit, added 2026-10-09):** the server refuses paths outside the `--root` folder and links that point out of it, but it cannot stop another local process that replaces a folder in the path at the same moment as a call (Node has no way to open a path relative to a held folder handle); the guide states this. These runs did not test that case.
- **Not covered:** the MCP resource for Claude Code and the MCP prompt for both clients (not available in these configurations); Gemini CLI, Cursor and OpenCode (C5d). Step C stays partly open until C5d, or until the user accepts them as an exception.
